## Problem Statement

Kasir UMKM sudah hidup di produksi lewat **WAHA** (`31.97.66.39:3011`) → middleware webhook → `StudioUmkmService`. Tim ingin **migrasi ke Hermes** dengan **setiap uji coba di server** (`master-production`), bukan hanya sidecar lokal. Hermes saat ini hanya ada di `docker-compose.yml` (smoke) dan **belum** ada di `docker-compose.master-production.yml`.

Hermes Agent bukan drop-in WAHA: default-nya **LLM agent + gateway**, bukan HTTP pipe. Migrasi yang salah mengganti brain kasir, bukan transport.

## Target User & Narrowest Wedge

**User:** pemilik/kasir warung kelontong pilot (`umkm-warung-klontong-bahagia`).

**Wedge:** Hermes sebagai **transport only** — inbound forwarded to existing webhook, outbound via adapter — tanpa mengubah matcher, confirm `ya`, atau pending sale. Cutover via env flag setelah adapter lulus di server.

## Constraints

- Prod published ports fixed: `8090`, `3013`, `3011`, `9010` — Hermes needs internal-only or replace WAHA port policy (decide before cutover).
- Do not stop non-`nsoft3-*` containers on co-host server.
- `volumes/hermes/` gitignored; prod data on server under bind mount.
- Baileys-class unofficial API — same ban/session-break risk as WAHA; not Cloud API.
- Hermes must **not** auto-reply as agent on kasir traffic (pipe-only).

## Premises

1. Hermes replaces **transport**, not `StudioUmkmService`.
2. All Hermes trials run on `31.97.66.39` / `master-production`.
3. Cutover is flag-driven with rollback (restore WAHA + volume) within one redeploy.
4. Baileys via Hermes; Cloud API deferred (TODOS.md D4.5).
5. Pilot tenant is highest-risk during cutover.

## Approaches Considered

### Approach A: Hermes infra smoke on server only
Add Hermes to prod compose; WAHA stays live. Validates Docker, QR, dashboard. Does not migrate kasir.

### Approach B: WhatsAppProvider abstraction + controlled cutover (chosen)
Introduce provider interface; implement `WahaProvider` (wrap existing) and `HermesProvider` (Baileys bridge, pipe-only). Env `WHATSAPP_PROVIDER=waha|hermes`. Phase 1: deploy adapter with WAHA live. Phase 2: server QA on Hermes flag. Phase 3: maintenance window flip + disable WAHA service.

### Approach C: Big-bang without dual-run
Rejected for implementation order — same end state as B phase 3, but without proven adapter rollback.

## Recommended Approach

**Approach B** — honors server-first testing and user's cutover appetite while keeping rollback.

### Architecture

```
INBOUND (Hermes mode):
  WhatsApp user
    → Hermes Baileys bridge (gateway)
    → pre_gateway_dispatch hook OR bridge forward
    → POST /api/studio/whatsapp/webhook (same payload shape as today)
    → StudioWhatsAppService (unchanged)

OUTBOUND:
  StudioWhatsAppService
    → WhatsAppProvider.sendText|sendList|sendImage|...
    → HermesProvider → bridge send API
    (WahaProvider → WahaClientService during phase 1)
```

### Server compose changes (`docker-compose.master-production.yml`)

1. Add `hermes` service: `image: ${HERMES_IMAGE:-nousresearch/hermes-agent:<pinned>}` (pin tag in `.env.master-production`; never bare `:latest` on prod), `command: gateway run`, bind `./volumes/hermes:/opt/data`.
2. Middleware reaches Hermes at **`http://hermes:8642`** on `nsoft3-net` (container port). Host offset `8652` is for SSH tunnel only — not middleware.
3. **Do not publish** Hermes gateway/dashboard on public IP initially.
4. Keep `waha` until Phase 3; after cutover stop service but **retain `waha-sessions` volume 7–14 days** for rollback.

### Hermes config (pipe-only)

In `/opt/data` (server `volumes/hermes`):

- `WHATSAPP_ENABLED=true`, `WHATSAPP_MODE=bot`
- `WHATSAPP_ALLOWED_USERS` = pilot allowlist (same numbers as `studio_whatsapp` allowlist)
- **Pipe-only (hard gate):** Phase 1 server probe must pick ONE path and document it in `docs/hermes-local.md` prod section:
  - **Preferred:** `pre_gateway_dispatch` hook → `skip` agent + HTTP POST raw inbound to middleware webhook.
  - **Fallback:** bridge forward config if hook proves insufficient on pinned image.
- `reply_prefix: ""`; `whatsapp.unauthorized_dm_behavior: ignore` for non-allowlist.
- Forwarder must **HMAC-sign** raw body with `WAHA_WEBHOOK_HMAC_KEY` (same header `x-webhook-hmac` middleware expects today).

**Hard prerequisite:** No Phase 2 adapter work until pipe-only + HMAC + one inbound/outbound round-trip documented from server.

### Phased rollout (all on server)

**Constraint:** one WhatsApp Web session per phone — pilot number cannot be active on WAHA and Hermes simultaneously.

| Phase | WHATSAPP_PROVIDER | WAHA | Hermes | Proof |
|-------|-------------------|------|--------|-------|
| 0 | waha | pilot # | off | Baseline QA (existing) |
| 1 | waha | pilot # | **test #** paired, pipe-only config documented | Hermes health + forward + HMAC + no agent reply |
| 2 | hermes | pilot # | **test #** full cycle | `jual → ya → omzet` on test number matches WAHA baseline; sendList tap or text fallback documented |
| 3 | hermes | **stopped** | **pilot #** re-QR in maintenance window | Pilot smoke on real tenant; no pending UMKM confirm in flight |
| Rollback | waha | **start** | stop | See runbook below (<30 min target) |

### Cutover checklist (Phase 3)

1. Announce maintenance; confirm **no pending sale/purchase** in DB for pilot tenant.
2. Stop `nsoft3-waha` (session released).
3. Pair Hermes on **pilot number** (new QR scan).
4. Set `WHATSAPP_PROVIDER=hermes`; redeploy middleware + hermes; verify session WORKING.
5. Server QA: sale, purchase, omzet, stok, pendamping alias.
6. Monitor middleware logs + Hermes `bridge.log` 24h (manual; no new alerting stack required).

### Rollback runbook (target <30 min)

1. (0–5 min) Set `WHATSAPP_PROVIDER=waha` in `.env.master-production`.
2. (5–10 min) `docker compose ... up -d waha`; stop hermes.
3. (10–20 min) If WAHA session invalid → re-scan QR on WAHA dashboard `:3011`.
4. (20–30 min) Smoke: one inbound + `sendText` reply on pilot allowlist.

### Observability

- Structured log: `provider=waha|hermes` on webhook + every outbound send.
- Phase 3: manual `docker logs nsoft3-middleware` + Hermes bridge log tail.
